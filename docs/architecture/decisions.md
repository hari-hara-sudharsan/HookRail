# HookRail — Architecture Decision Record

Status: Initial decisions accepted; details remain subject to validation through implementation and testing.

## Product and delivery

| Area | Decision |
|---|---|
| Primary audience | Payment platforms |
| Expansion audience | SaaS event producers |
| Delivery semantics | At-least-once |
| Initial sustained benchmark target | 100 events/second |
| Initial burst benchmark target | 1,000 events/second |
| Destinations | Multiple subscribed destinations per event |
| Customer interface | API plus comprehensive dashboard, built incrementally |

At-least-once means HookRail retries eligible deliveries according to policy and duplicate deliveries are possible. It does not promise exactly-once execution of a merchant business operation.

## Infrastructure

| Area | Decision |
|---|---|
| Backend language | Go |
| Primary database | PostgreSQL |
| Initial job queue | PostgreSQL-backed |
| Future queue option | Evaluate Kafka only when justified |
| Payload storage | S3-compatible object storage |
| Local object storage | MinIO |
| Local orchestration | Docker Compose |
| Architecture direction | Service-oriented / microservices direction, with service boundaries validated incrementally |

The PostgreSQL-backed queue avoids an initial database-to-broker dual-write boundary. If Kafka is introduced, evaluate a transactional outbox or equivalent reliable publication mechanism.

## Data model direction

Initial logical entities:

- Tenant: customer account and isolation boundary.
- Destination: tenant-owned endpoint and subscription configuration.
- Event: immutable event identity, type, tenant, payload reference, and payload hash.
- Delivery job: independent lifecycle for one event-destination pair.
- Delivery attempt: record of each HTTP attempt and its outcome.
- Idempotency record: tenant-scoped producer request key and original acceptance result, protected by a unique constraint.

Expected uniqueness rules include:

- (tenant_id, idempotency_key) for producer submission deduplication.
- (event_id, destination_id) for one logical delivery job per destination.

A repeated idempotency key with a different canonical request fingerprint must be rejected as a conflict, not treated as a valid replay.

## Durability and payload storage

The ingestion path must not acknowledge acceptance until:
1. The payload has been successfully written and verified in object storage.
2. The event metadata and all initial delivery jobs have committed atomically in PostgreSQL.

Object storage and PostgreSQL do not share a transaction. The implementation must therefore handle orphaned objects, upload failures, database failures after upload, and reconciliation. A database row must never become deliverable while its referenced payload is unavailable.

Object keys should be generated by HookRail, not accepted directly from producers. Payloads should be immutable after acceptance.

## Worker coordination and recovery

- Workers claim jobs through short PostgreSQL transactions and row locking, for example SELECT FOR UPDATE SKIP LOCKED.
- Do not hold database row locks while making outbound HTTP requests.
- Claims use time-bounded leases.
- Expired leases are recovered by a scheduler/sweeper.
- A worker may crash after the merchant processes a request but before HookRail records success. Retrying is necessary for at-least-once behavior and can result in duplicate delivery.
- Record each attempt and its outcome; define terminal and retryable failure classifications explicitly.

## Security

- Tenant-scoped authentication and authorization.
- Secure API-key lifecycle and storage.
- HMAC webhook signatures with timestamp/replay protections and secret rotation.
- Egress SSRF defense: validate schemes, resolve and inspect addresses, block prohibited networks, protect against DNS rebinding, and validate the actual connection destination.
- Do not permit redirects to bypass outbound destination validation.
- Apply per-tenant and per-destination quotas.
- Keep secrets out of logs and payload inspection views.

## Read models and dashboard

A read replica may be used for analytics/history when justified. It is not authoritative for worker claims, delivery transitions, or decisions that require fresh state because replica lag is possible.

The dashboard will be built incrementally on secured APIs. Replay must be an explicit, audited operation and must preserve original event identity while creating a clearly defined new delivery/replay record or generation.

## Decisions deliberately deferred

- Kafka adoption.
- Multi-region active-active or failover design.
- Exact service deployment boundaries.
- Read-replica introduction.
- Final retry schedule and limits.
- Final rate-limit algorithm and quotas.
- Exact performance SLOs beyond initial benchmark targets.
- Production cloud provider and object-store configuration.

These require workload measurements, threat modeling, or further design.

## Important terminology

An HTTP success response indicates that the destination endpoint returned a success response. It does not prove that all downstream business effects completed. Consumers remain responsible for idempotent processing.
